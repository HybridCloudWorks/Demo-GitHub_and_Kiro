# Chatting with Kiro

> **Level:** L2 · **Estimated time:** 12 min · **Prerequisites:** the workspace lesson

## 🎯 Objectives

By the end of this lesson you will be able to:

- Ask Kiro questions about your code
- Request a change and review what Kiro proposes
- Write clearer prompts to get better results

## 📖 Lesson

### Talking in plain language

Kiro chat is a conversation. You can ask things like:

- "What does `app.js` do?"
- "Add a footer to `index.html` with the current year."
- "Why is my page not applying the styles?"

Kiro reads the relevant files in your workspace and responds — often proposing concrete edits
you can review and apply.

### Writing effective prompts

The clearer your request, the better the result. A useful shape:

1. **Context** — what/where. *"In `index.html`…"*
2. **Goal** — what you want. *"…add a section listing what I've learned…"*
3. **Constraints** — any rules. *"…keep it plain HTML, no frameworks."*

Compare:

| ❌ Vague | ✅ Clear |
|----------|----------|
| "make it better" | "Increase the heading size and add more spacing between cards in `styles.css`." |
| "add a thing" | "Add a bulleted list in `index.html` under a heading 'What I've learned'." |

### Review before you accept

When Kiro proposes changes, **read them**. You're always in control — you decide what to keep.
This habit is how you learn *and* stay safe.

:::tip Iterate
If the first result isn't quite right, say what to change: "Good, but make the list numbered
instead of bulleted." Small follow-ups beat one giant prompt.
:::

## ✅ Checkpoint

- [ ] I asked Kiro a question about a file and understood the answer.
- [ ] I requested a change using context + goal + constraints.
- [ ] I reviewed a proposed change before accepting it.

## 🧪 Demo / Try it

Open your course repo in Kiro and ask: *"Explain what `labs/_grader/grade.js` does in two
sentences."* Read the answer — notice how Kiro used the actual file to respond.
